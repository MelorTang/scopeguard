# Windows Execution Permission and Terminal Process Boundary

Research snapshot: 2026-08-13
Decision update: 2026-08-14
Tracks: [GitHub issue #5](https://github.com/MelorTang/scopeguard/issues/5)
Target: Windows 10/11 x64, as selected by [ADR-0010](../adr/0010-target-windows-first.md)

## Executive decision

ScopeGuard V1 can make reliable **application-level** guarantees for operations that remain inside a ScopeGuard-controlled broker: typed file reads and writes, approval decisions, and HTTP requests made through a mandatory application network client. Those guarantees require fail-closed validation at the point of use; a displayed path, normalized string, current working directory, or earlier approval is not itself an enforcement boundary. Windows exposes several path namespaces, reparse points, alternate data streams, and hard links, so robust file mediation must validate the opened object, not only the requested string. [Microsoft: Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file), [Microsoft: Reparse Points and File Operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations), [Microsoft: Hard Links and Junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)

An ordinary approved command, script, CLI agent, or PowerShell process is not confined to the Workspace or to declared network destinations. A Windows process created normally runs in the caller's security context, and `cwd` only selects its initial current directory. It may use any file, credential, IPC, process, or network authority available to the signed-in Member. PowerShell execution policy is explicitly not a security system. ScopeGuard must therefore replace ordinary launch with an OS-enforced Managed Execution Sandbox for all Agent-triggered code in the two bounded profiles. [Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [Node.js: `child_process`](https://nodejs.org/api/child_process.html), [Microsoft: about_Execution_Policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies)

Therefore, the V1 meaning of the three profiles should be:

- **Request Approval:** automatic brokered reads inside the Workspace; Member review for eligible writes, network uses, outside paths, and command/script launches. Every approved executable still runs inside an immutable, per-run OS sandbox policy.
- **Auto Approve:** the same broker and Managed Execution Sandbox, with an automatic reviewer deciding eligible requests. Reviewer choice never expands or removes the sandbox boundary.
- **Full Access:** no Managed Execution Sandbox or per-operation application gate for local files, command/script launches, or network. It is explicit current-user ambient authority, not elevation.

This interpretation implements [ADR-0014](../adr/0014-govern-local-access-per-conversation.md) and [ADR-0022](../adr/0022-require-a-managed-execution-sandbox.md) by separating reviewer decisions from resource confinement. The Windows sandbox mechanism remains prototype-gated: AppContainer/LPAC, restricted tokens and DACLs, Windows Sandbox or a VM, and any firewall/WFP component must be qualified against the required compatibility and escape-resistance matrix. Until one design passes, bounded profiles must fail closed for arbitrary local execution rather than fall back to an ordinary process. [Microsoft: Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), [Microsoft: Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/), [Microsoft: Windows Filtering Platform ALE](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-)

## Scope and assurance vocabulary

This research assumes a normally installed per-user Electron application running unelevated as the signed-in Windows Member. It distinguishes these threat actors:

- **Accidental or model-originated misuse:** an operation reaches a path or endpoint that was not intended by the Member.
- **Untrusted launched code:** an approved command, script, package lifecycle hook, CLI agent, or terminal program deliberately tries to exceed its declared scope.
- **Same-user process:** malware or another application already running as the same Windows user.
- **Administrator or kernel compromise:** an administrator, service, driver, or compromised operating system.

The assurance labels used below are:

- **Application-enforced:** reliable while every relevant operation must pass through a ScopeGuard broker and no equivalent bypass is exposed to the actor.
- **Lifecycle-enforced:** ScopeGuard can account for and terminate participating processes, but does not restrict their authority.
- **OS-enforced:** Windows checks a restricted token, DACL, firewall/WFP filter, or hypervisor boundary independently of ScopeGuard's JavaScript logic.
- **Best effort:** useful operational behavior that must not be represented as containment.

Electron's renderer sandbox limits renderer capabilities and delegates privileged work to the main process; Electron utility processes expose Node.js APIs. The renderer sandbox therefore does not confine main-process, utility-process, Node child-process, or PTY activity. [Electron: Process Sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox), [Electron: Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Electron: `utilityProcess`](https://www.electronjs.org/docs/latest/api/utility-process)

## Contract and current implementation baseline

The domain contract in [CONTEXT.md](../../CONTEXT.md) separates a Workspace, a per-Conversation Execution Profile, and an unmanaged Workspace Terminal. [ADR-0014](../adr/0014-govern-local-access-per-conversation.md) makes the profile local and Conversation-scoped; [ADR-0015](../adr/0015-share-live-workspaces-with-conflict-detection.md) requires operations against the live directory with conflict detection; [ADR-0018](../adr/0018-offer-an-unmanaged-workspace-terminal.md) places the terminal outside Conversation, Agent, Harness, and profile semantics. [ADR-0011](../adr/0011-allow-offline-access-to-local-work.md) requires OS-account-bound local protection and names Windows Credential Manager.

At commit [`26b2b48e`](https://github.com/MelorTang/scopeguard/tree/26b2b48e2432c566301af8d522a117baa483b1de), the native file tools use Node `realpath`, a relative-path test, and open-file I/O; writes reject a final symbolic-link target and use a temporary file plus rename. This is a useful application-level baseline, but it does not inspect every Windows reparse component, reject alternate streams/device namespaces, detect hard links, or verify a final Windows handle identity. [ScopeGuard: file tools](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/packages/tool-runtime/src/index.ts#L106-L295), [ScopeGuard: path resolution](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/packages/tool-runtime/src/index.ts#L340-L395)

The current command tool passes an approved string to `cmd.exe /d /s /c`, with the Workspace as `cwd`, and cancellation invokes `taskkill /t` followed by `/f`. This is an approval gate plus best-effort tree termination, not file or network confinement. Microsoft documents `/t` as terminating the selected process and child processes it started; unlike a Job Object assigned at creation, it does not establish a persistent membership boundary. [ScopeGuard: command launch](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/packages/tool-runtime/src/index.ts#L297-L337), [ScopeGuard: shell invocation](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/packages/tool-runtime/src/index.ts#L415-L436), [ScopeGuard: Windows termination](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/packages/tool-runtime/src/index.ts#L617-L648), [Microsoft: `taskkill`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill)

Provider secrets currently use Electron `safeStorage`, which uses DPAPI on Windows, while local application data uses an ordinary `node:sqlite` database in WAL mode. The database, WAL, shared-memory, and journal files receive POSIX-style `chmod` calls, but Node documents that Windows implements only the write bit and does not implement distinct owner/group/other permissions. The current database and cache must therefore be treated as plaintext at rest unless an encrypted SQLite build or application-layer encryption is added. [ScopeGuard: encrypted secret vault](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/apps/desktop/src/main/encrypted-secret-vault.ts#L19-L74), [ScopeGuard: SQLite open](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/packages/storage-sqlite/src/index.ts#L68-L88), [ScopeGuard: database file modes](https://github.com/MelorTang/scopeguard/blob/26b2b48e2432c566301af8d522a117baa483b1de/packages/storage-sqlite/src/index.ts#L2789-L2803), [Node.js: `fs.chmod` on Windows](https://nodejs.org/api/fs.html#fschmodpath-mode-callback)

## 1. Path confinement for brokered file operations

### What the V1 file broker can guarantee

For a typed file operation implemented entirely by ScopeGuard, V1 can guarantee that the opened object was inside the approved Workspace at the moment it was opened, subject to the Windows access checks of the current user. The guarantee should be based on a Windows file handle: `CreateFileW` opens a file/device and returns a handle, while `GetFinalPathNameByHandleW` returns the fully resolved path, including resolution across symbolic links. [Microsoft: `CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Microsoft: `GetFinalPathNameByHandleW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew)

The V1 broker should:

1. Accept Workspace-relative paths only for Workspace-scoped operations; reject drive-relative, absolute drive, UNC, `\\?\`, `\\.\`, NT device, reserved DOS device, and alternate-data-stream syntax before access. Windows treats these as distinct path forms, and a colon can name a file stream. [Microsoft: Naming Files, Paths, and Namespaces](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file), [Microsoft: File Streams](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams)
2. Open and retain a handle to the canonical Workspace root. For each operation, open the final object with the minimum access and restrictive sharing needed, retrieve its normalized final path/volume identity, compare it case-insensitively to the root boundary, and perform read/write through the validated handle. `GetFinalPathNameByHandleW` is specifically defined to return the fully resolved path. [Microsoft: `GetFinalPathNameByHandleW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew)
3. Inspect path components without following reparse points, reject unexpected reparse tags, and fail closed if verification is unavailable. `FILE_FLAG_OPEN_REPARSE_POINT` disables normal reparse processing for the object being opened; reparse behavior otherwise depends on the operation and tag. [Microsoft: `CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Microsoft: Reparse Points and File Operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations)
4. Reject multiply linked files when strict Workspace-only identity is required, or explicitly downgrade the guarantee. NTFS hard links allow multiple paths on one volume to reference the same file, so no canonical path string proves that the object has no outside-Workspace name. [Microsoft: Hard Links and Junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions), [Microsoft: `BY_HANDLE_FILE_INFORMATION`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information)
5. For replacement writes, create the temporary object in the already validated parent directory, preserve [ADR-0015](../adr/0015-share-live-workspaces-with-conflict-detection.md)'s editable-read hash check, verify the destination again immediately before replacement, replace atomically, and fail on identity or content drift. Windows sharing modes remain attached to an open handle and can prevent conflicting opens, but they do not turn a path string into a permanent identity. [Microsoft: `CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Microsoft: `SetFileInformationByHandle`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle)

This is an application-enforced guarantee for the broker's own operation. It is not a DACL sandbox around the Workspace, and it does not prevent another process running as the Member from editing the same live files before or after that operation. Windows file access is ultimately controlled by security descriptors and DACLs. [Microsoft: File Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [Microsoft: Access-Control Lists](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-lists)

### What the file broker alone cannot guarantee

`realpath` and prefix checks are not sufficient as an adversarial Windows boundary. Node defines `realpath` as canonical resolution, but hard links and concurrent namespace changes mean path identity is not unique or stable; Windows reparse points can also redirect file operations. A normally launched command can bypass the broker and call Windows APIs directly. [Node.js: `fs.realpath`](https://nodejs.org/api/fs.html#fsrealpathpath-options-callback), [Microsoft: Hard Links and Junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions), [Microsoft: Reparse Points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points)

OS-enforced confinement requires a different principal or isolation layer. An AppContainer combines the user's rights with an AppContainer SID/capability check, so access is the intersection of both grants and resources must be explicitly made available. Windows Sandbox or a VM provides a stronger machine boundary, with mapped host folders becoming deliberate exposure points. [Microsoft: Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), [Microsoft: Windows Sandbox configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

## 2. Commands, scripts, and profile semantics

Node distinguishes direct executable launch from shell execution: `exec` runs through a shell, while `execFile` launches directly; on Windows, `.bat` and `.cmd` files require a terminal/shell path. Node also warns that unsanitized shell input may execute arbitrary commands. ScopeGuard should therefore model an execution request as immutable `executable`, `argv`, `cwd`, environment names, script/content hash, and timeout whenever direct execution is possible, and show the exact shell string plus shell identity when a shell is unavoidable. [Node.js: `child_process.execFile`](https://nodejs.org/api/child_process.html#child_processexecfilefile-args-options-callback), [Node.js: Windows batch files](https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows)

An approval applies to exactly that launch specification and immutable sandbox policy and must expire after use or any mutation. It cannot meaningfully approve each later file, registry, process, credential, or socket operation performed by the child. Request Approval therefore combines a Member-reviewed launch gate with OS enforcement for all later effects; approval alone is insufficient. [Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [Microsoft: AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)

`Auto Approve` uses the same immutable sandbox-policy compiler and OS-enforced runner. Its automatic reviewer may approve only operations representable within that boundary; an unenforceable request is denied or handed to Full Access as an explicit Member choice, never launched unsandboxed. Treating a script signature, command allowlist, PowerShell execution policy, or Workspace `cwd` as confinement would be incorrect: PowerShell documents execution policy as a safety feature rather than a security system and states that users can bypass it. [Microsoft: about_Execution_Policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies)

`Full Access` removes the Managed Execution Sandbox and ScopeGuard's launch prompt, but the process still runs only with the current user's token unless a separate Windows elevation flow occurs. ScopeGuard should neither request elevation for normal runs nor silently translate Full Access into administrator access. Windows creates a normal process in the caller's security context; starting with alternate credentials or a different token uses separate APIs and policy. [Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [Microsoft: Processes in the Client Security Context](https://learn.microsoft.com/en-us/windows/win32/secauthz/processes-in-the-client-security-context)

## 3. Network controls

ScopeGuard can reliably enforce per-Conversation network declarations only for requests routed through one mandatory application broker. The broker should normalize and bind scheme, destination host/IP, port, method, and redirect policy before dispatch, re-check redirects, and retain only the bounded outcome state needed to present or recover the Run. Electron's `webRequest` observes requests for a specific `Session`, and Electron's `net`/`fetch` can use that session; these hooks do not cover sockets opened by arbitrary Node modules or subprocesses. [Electron: `webRequest`](https://www.electronjs.org/docs/latest/api/web-request), [Electron: `net`](https://www.electronjs.org/docs/latest/api/net)

A Full Access process or unmanaged terminal can create sockets independently of Electron. A bounded-profile process must instead start with network denied unless the qualified sandbox design can enforce its immutable network policy. Windows Firewall allows outbound traffic by default unless a blocking rule matches, and Microsoft recommends program/path rules for applications. Such machine policy is outside a per-Conversation JavaScript broker; administering firewall behavior normally requires an elevated command prompt. [Microsoft: Configure Windows Firewall rules](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure), [Microsoft: `netsh advfirewall`](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/netsh-advfirewall-firewall-control-firewall-behavior)

WFP's Application Layer Enforcement layers can authorize connect operations using application and user identity, but WFP is a system network-policy architecture, not an Electron API. A rule keyed to one shared executable also does not inherently express ScopeGuard's Conversation instance; per-run enforcement would require a privileged broker/service and a carefully designed identity or isolation mapping. This is an architectural inference from WFP's documented application identification and connect-authorization model. [Microsoft: WFP ALE](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-), [Microsoft: WFP access control](https://learn.microsoft.com/en-us/windows/win32/fwp/access-control)

AppContainer can enforce network denial by omitting network capability. If granted `internetClient`, fine-grained host/method policy must still be supplied by a qualified broker or OS policy rather than inferred from the broad capability. Windows Sandbox can disable networking in its `.wsb` configuration; a VM can provide an equivalent external boundary. The MVP may keep subprocess networking denied if endpoint-scoped enforcement does not pass the prototype. [Microsoft: Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), [Microsoft: Windows Sandbox configuration](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

## 4. Process trees, cancellation, and termination

A Windows Job Object is the correct V1 primitive for lifecycle ownership inside both the Managed Execution Sandbox and the unmanaged terminal, but it is not the sandbox itself. A job manages associated processes as a unit; ordinary `CreateProcess` children inherit membership by default, `TerminateJobObject` terminates current members, and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` terminates members when the last job handle closes. ScopeGuard should assign a dedicated command-run or terminal-host process to its job at creation using `PROC_THREAD_ATTRIBUTE_JOB_LIST`, disable both breakaway flags, retain the job handle, and wait for the job to become empty on cancellation or shutdown. [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Microsoft: `UpdateProcThreadAttribute`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [Microsoft: `TerminateJobObject`](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject)

Assignment at creation avoids the race in launching a process and assigning it afterward. The job should not allow explicit or silent breakaway. This choice may make software that insists on its own incompatible Job Object fail; V1 should surface that as an execution incompatibility rather than weakening the lifecycle claim. Microsoft also documents an exception: children created through `Win32_Process.Create` do not automatically join the job. [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

A Job Object is not a security sandbox. Microsoft states that security limits must be set individually on processes; job limits chiefly provide grouping, accounting, resource limits, and termination. It cannot revoke current-user file, credential, registry, IPC, or network authority, and termination cannot undo writes or network requests already completed. [Microsoft: Job Object Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/procthread/job-object-security-and-access-rights), [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

`taskkill /t` remains a reasonable fallback, not the primary guarantee. Node's `subprocess.killed` only records that a signal was sent successfully and does not indicate that the child terminated. V1 should report cancellation as `terminated` only after the Job Object is empty; timeout, API failure, or unverifiable membership must be reported as `termination_unconfirmed`, never as success. [Microsoft: `taskkill`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill), [Node.js: `subprocess.killed`](https://nodejs.org/api/child_process.html#subprocesskilled)

## 5. ConPTY and upstream `node-pty`

Microsoft ConPTY is a pseudoconsole transport, not a security boundary. A client creates a pseudoconsole and then starts a process with the pseudoconsole attribute; the process still has its normal Windows token. The upstream `node-pty` README is explicit that spawned processes run at the same permission level as the parent and recommends containers when stronger isolation is required. [Microsoft: Creating a Pseudoconsole Session](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session), [`node-pty` README: security](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/README.md#L117-L120)

The pinned upstream source does not create a Job Object when it creates the ConPTY process. Its Windows `kill()` path asks the console for process IDs and calls `process.kill`; the TypeScript API also states that Unix signals are unsupported on Windows. Closing the pseudoconsole closes ConPTY resources, but this is not equivalent to persistent Job Object membership. [`node-pty`: Windows terminal kill](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/src/windowsTerminal.ts#L166-L179), [`node-pty`: console-process enumeration](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/src/windowsPtyAgent.ts#L196-L240), [`node-pty`: ConPTY process creation](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/src/win/conpty.cc#L395-L475), [`node-pty` typings](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/typings/node-pty.d.ts#L176-L188)

Recommended terminal architecture: one dedicated, unprivileged PTY host process per tab; put that host into a no-breakaway Job Object atomically at creation; let the shell inherit membership; keep all PTY pipes and the job handle outside the renderer; on close, request graceful exit, then terminate and verify the job, then close/drain ConPTY from a worker that cannot block the Electron main thread. `ClosePseudoConsole` sends `CTRL_CLOSE_EVENT`; before Windows 11 24H2 it can wait indefinitely if the output pipe is not closed or drained. [Microsoft: `ClosePseudoConsole`](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole), [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

ConPTY's documented minimum client is Windows 10 version 1809. The pinned `node-pty` README gives the stricter Windows support requirement of Windows 10 1809, build 18309 or later. V1 should runtime-gate the terminal to the upstream-supported build and test both supported Windows 10 x64 and Windows 11 x64; the rest of the Desktop may continue to follow ADR-0010 independently. [Microsoft: `ClosePseudoConsole` requirements](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole), [`node-pty` README: platform support](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/README.md#L12-L18)

## 6. Credential Manager, DPAPI, and secret exposure

Windows Credential Manager and DPAPI are related account-bound storage options, but they are not the same API. `CredWriteW` stores credentials associated with the current token's logon session, and `CredReadW` reads that credential set; a generic credential can persist for the same user on the same machine. This directly matches ADR-0011's literal requirement and is appropriate for small opaque grants and an application data-encryption key. [Microsoft: `CredWriteW`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew), [Microsoft: `CredReadW`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw), [Microsoft: `CREDENTIALW`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)

Electron `safeStorage` uses DPAPI on Windows. Electron states that it protects data from other users on the same machine but not from other applications in the same userspace. DPAPI normally ties decryption to the same logon credentials and machine and adds integrity protection; `CRYPTPROTECT_LOCAL_MACHINE` must not be used for ScopeGuard user data because Microsoft states that any user on that computer can decrypt data protected with that flag. [Electron: `safeStorage`](https://www.electronjs.org/docs/latest/api/safe-storage), [Microsoft: `CryptProtectData`](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)

V1 should use one documented Windows backend consistently:

- To satisfy ADR-0011 literally, use Credential Manager generic credentials for the offline grant and a random local data key; store only ciphertext and non-secret references in application files.
- If Electron `safeStorage` remains the implementation, document it as DPAPI-backed OS-account protection rather than claiming Windows Credential Manager, and resolve that contract difference before release.
- Apply an explicit DACL to the private application-data directory and verify it after creation. Windows files otherwise inherit access-control entries from the parent, and `SetNamedSecurityInfoW` is the native API for setting a DACL. [Microsoft: File Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [Microsoft: `SetNamedSecurityInfoW`](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setnamedsecurityinfow)

Neither backend protects secrets after ScopeGuard decrypts them into its process, nor from an unrelated same-user process, Full Access process, or unmanaged terminal capable of invoking the same user-scoped APIs or inspecting accessible local state. The Managed Execution Sandbox must deny ambient access to those stores, but Provider/MCP credentials that must also remain outside Full Access commands and the unmanaged terminal must remain server-held and must never be copied into local files, command arguments, environment variables, terminal input, or child-process IPC. The same-user limitation is explicit in Electron's `safeStorage` documentation and follows from Credential Manager's current-token credential set. [Electron: `safeStorage`](https://www.electronjs.org/docs/latest/api/safe-storage), [Microsoft: `CredReadW`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)

## 7. Local database and cache encryption

The V1 local database, transcripts, context revisions, artifacts, cached search data, and spill/temp files require encryption at rest in addition to a DACL. Node's `DatabaseSync` opens a file-backed SQLite database but does not expose a database-encryption guarantee. SQLite's official SEE extension encrypts all database content and rollback/WAL content while data remains plaintext in memory; its documentation also notes that temporary files used for temporary tables and indexes are not encrypted. [Node.js: SQLite `DatabaseSync`](https://nodejs.org/api/sqlite.html#class-databasesync), [SQLite: Encryption Extension](https://www.sqlite.org/see/doc/trunk/www/readme.wiki), [SQLite: Professional Support and SEE](https://www.sqlite.org/support.html)

Recommended V1 storage design:

1. Generate a per-installation 256-bit data-encryption key and wrap/store it under the selected current-user Credential Manager or DPAPI backend. Fail closed when the key cannot be recovered; never open a plaintext fallback database.
2. Use a supported SQLite encryption build that covers the main database and WAL/rollback journal, or use authenticated application-layer encryption for every sensitive field/blob. With field encryption, schema, row counts, indexes, and any deliberately queryable metadata remain visible and must be classified as non-secret.
3. Keep sensitive parse/search caches inside the encrypted store or encrypt sidecar files with the same key hierarchy. Disable or redirect plaintext temporary storage and securely discard migration plaintext; SEE itself documents that SQLite temporary files are outside its database encryption. [SQLite: Encryption Extension](https://www.sqlite.org/see/doc/trunk/www/readme.wiki)
4. Set and verify an explicit private-directory DACL. Do not treat `chmod(0600)` as a Windows ACL because Node documents that owner/group/other distinctions are not implemented on Windows. [Node.js: `fs.chmod`](https://nodejs.org/api/fs.html#fschmodpath-mode-callback), [Microsoft: Access-Control Lists](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-lists)

This protects against offline copying and other non-privileged user accounts when the key remains unavailable. It does not protect plaintext while ScopeGuard is unlocked, a same-user process that can use the same account-bound key, an administrator that can change ownership/access, or a compromised kernel. BitLocker is still valuable for lost/stolen-device and offline-volume protection, but it is device posture administered outside ScopeGuard and is not a substitute for application database encryption. [Microsoft: BitLocker overview](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/)

## 8. Unmanaged PowerShell terminal boundary

Per [ADR-0018](../adr/0018-offer-an-unmanaged-workspace-terminal.md), the Workspace Terminal is intentionally outside Conversations, Agents, Harnesses, and Execution Profiles. Its defensible V1 contract is: an explicit Member opens a PowerShell tab rooted at the Workspace; the shell runs unelevated as the current Windows user; ScopeGuard owns the PTY lifecycle and terminal rendering; filesystem-monitor events invalidate stale editable-read hashes; closing the tab or Desktop terminates verified Job Object members.

The terminal must be labeled by behavior, not as sandboxed. Its initial directory is convenience only. It may read/write outside the Workspace, use the network, access same-user credentials, launch GUI/background/brokered processes, and alter files without ScopeGuard approval. Upstream `node-pty` states that children have the parent's permissions, and Windows Job Objects provide process grouping rather than per-process security limits. [`node-pty` README: security](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/README.md#L117-L120), [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

ScopeGuard must not inject enterprise provider, MCP, organization, or server credentials into the terminal. Local credentials already available to the current Windows user are outside ScopeGuard's ability to conceal from that same user/session. Terminal close can guarantee termination only for verified Job Object members; it cannot revoke completed side effects or claim control over processes created through documented non-member paths such as `Win32_Process.Create`. [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Microsoft: `CredReadW`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)

## Explicit V1 Non-Guarantees

ScopeGuard V1 must state all of the following without qualification:

1. A Workspace path, canonical path, or Workspace `cwd` is not an OS sandbox. Bounded-profile code is confined only when the Managed Execution Sandbox is established and verified; Full Access and the unmanaged terminal are not confined. [Microsoft: `CreateProcessW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [Node.js: `cwd` in `spawn`](https://nodejs.org/api/child_process.html#child_processspawncommand-args-options)
2. `Request Approval` and `Auto Approve` choose different reviewers but use the same sandbox. An approval can select a prevalidated policy expansion; it cannot authorize an unenforced or silently unsandboxed launch. [Microsoft: AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)
3. `Full Access` is current-user ambient authority without the Managed Execution Sandbox or ScopeGuard prompts. It is not administrator elevation. [Microsoft: `CreateProcessW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)
4. Electron renderer sandboxing does not sandbox the Electron main process, utility processes, Node children, ConPTY, or PowerShell. [Electron: Process Sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox), [Electron: Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model)
5. A Job Object, `taskkill /t`, `node-pty.kill()`, or `ClosePseudoConsole` does not restrict file/network/credential authority and cannot undo completed side effects. ScopeGuard guarantees termination only for verified Job Object members and reports all other cases as unconfirmed. [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [`node-pty`: Windows kill](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/src/windowsPtyAgent.ts#L196-L240), [Microsoft: `ClosePseudoConsole`](https://learn.microsoft.com/en-us/windows/console/closepseudoconsole)
6. The unmanaged terminal is outside all Conversation Execution Profiles. Its initial Workspace directory is convenience, not confinement. [`node-pty` README: security](https://github.com/microsoft/node-pty/blob/7822654b683c0a24a3d3b30f6e97b4139655ca66/README.md#L117-L120), [Microsoft: `CreateProcessW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)
7. Electron `webRequest` or an application HTTP allowlist does not control sockets opened by a subprocess or unmanaged terminal. [Electron: `webRequest`](https://www.electronjs.org/docs/latest/api/web-request), [Microsoft: Configure Windows Firewall rules](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure)
8. PowerShell execution policy, command allowlists, script hashes/signatures, and exact-command approval are decision controls, not hostile-code containment. [Microsoft: about_Execution_Policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies), [Microsoft: Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)
9. Credential Manager, DPAPI/`safeStorage`, private DACLs, and encrypted SQLite do not protect unlocked plaintext from unrelated same-user code, Full Access code, the unmanaged terminal, administrators, or kernel compromise. The bounded-profile sandbox reduces ambient access but cannot protect secrets deliberately injected into a child. [Electron: `safeStorage`](https://www.electronjs.org/docs/latest/api/safe-storage), [Microsoft: `CredReadW`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw), [SQLite SEE](https://www.sqlite.org/see/doc/trunk/www/readme.wiki)
10. BitLocker protects the volume/device against offline loss scenarios; it is not a ScopeGuard database, process, or per-Conversation isolation guarantee. [Microsoft: BitLocker overview](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/)
11. Server-held provider/MCP/organization credentials remain outside local execution only if ScopeGuard never materializes them in local files, process environment, arguments, terminal input, logs, caches, or child IPC. This is a ScopeGuard architecture requirement derived from the same-user limitations of local protection. [Electron: `safeStorage`](https://www.electronjs.org/docs/latest/api/safe-storage), [Microsoft: `CredReadW`](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)
12. Hostile-code path/network confinement is an MVP release gate, not an application-only guarantee. It requires a qualified AppContainer/LPAC runner, restricted-token and DACL design, administrator-controlled firewall/WFP architecture, Windows Sandbox, or a VM, with explicit compatibility and host-resource exposure rules. Failure to qualify a runner defers arbitrary bounded-profile local execution; it does not weaken the product claim. [Microsoft: Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), [Microsoft: WFP ALE](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-), [Microsoft: Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)
